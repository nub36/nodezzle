# 12A — Аудит и контракт внутренних обращений

**2026-09-15. Аудит выполнен по коду 0.5.50.** Это спецификация для 12B–D,
не реализованные API/таблицы. UX-оболочка `/workspace/requests` уже есть,
но не является системой заявок. Решение: ADR-031 в `docs/DECISIONS.md`.

## 1. Что найдено в коде и что переиспользуем

| Механизм | Факт и путь | Дельта для обращений |
|---|---|---|
| Аккаунт | `server/src/routes/auth.ts`: currentUser, повторная проверка сессии; HttpOnly, scrypt | Та же аутентификация, без новой системы паролей |
| Пространства | `workspaces/store.ts`, `routes/workspaces.ts`, миграция 003: owner, workspace_members; проверяется isMember, не роль | Отдельные разрешения на обращения, **не** автоматическое членство в редакторском пространстве |
| Проекты/секреты | `routes/projects.ts`, `routes/secrets.ts`: доступ участников пространства к операциям | Сотруднику службы обращений нельзя автоматически выдавать этот доступ |
| БД | `db.ts`: SQLite/WAL/FK, последовательные SQL-миграции; последняя 012 | Новые таблицы обращений после 012, формат проекта v1 неизменен |
| Конкуренция | `routes/projects.ts`, `projects/store.ts`: expectedRevision и CAS | Повторить принцип условной записи, но с собственной ревизией заявки, не ревизией схемы |
| Telegram-вход | `routes/webhook.ts`: секретный путь, rate-limit, Zod; ошибка обработчика поглощается, возвращается 200 | Для обращений сначала надёжно сохранить входящее событие; ошибка хранения не подтверждается как приём |
| Источник события | `telegram/updates.ts`: updateId есть, message и edited_message объединяются; для message теряются message_id и chat.type | Сохранить тип события, message_id и тип чата в доверенном серверном конверте; редактирование не создаёт новую заявку |
| Выполнение/отправка | `telegram/handler.ts`: LIVE, лимиты, затем последовательная отправка outbox; ParallelLimitError приводит к возврату | Входящая очередь и состояние уведомлений; не терять заявку при перегрузке/ошибке отправки |
| Дедупликация | `executions.external_event_id` — поле трассировки без UNIQUE (миграция 009) | Не использовать журнал исполнений как защиту от повторов |
| Доставка | `telegram/api.ts`: таймаут/ошибки; нет долговременных заданий отправки | Отдельные подтверждённые/неудачные/неопределённые попытки, без обещания exactly-once в Telegram |
| Журналы | `execution/record.ts` сохраняет сводки входов/выходов; маскируются секреты, не произвольный текст обращений | Не допускать копирования текста заявок в общедоступный журнал/телеметрию конструктора |
| Конструктор | `RuntimeContext`, реестр, симулятор и серверный запуск уже есть | Узкий адаптер обращений в контексте выполнения, не ветвление ядра по специальным Telegram-ID |

Дополнительное расхождение: управление вебхуком передаёт secret_token,
но входящий маршрут сейчас не проверяет заголовок `X-Telegram-Bot-Api-Secret-Token`.
Секретный путь остаётся действующей защитой; проверку заголовка включить
в 12D с миграционной совместимостью и негативными тестами, до пилота.

## 2. Граница доступа — сначала безопасность

**Идентичность одна:** существующий `users` и текущая сессия. Участие
в обращениях хранится отдельно от `workspace_members`, поскольку последний
даёт доступ к редакторским проектам/секретам. Это отдельное разрешение,
а не вторая авторизация или второе рабочее пространство.

Роли обращений: `coordinator` и `employee`. Владелец пространства получает
права координатора; другим пользователям нужен активный допуск в обращения.
Само по себе редакторское членство не даёт права просматривать обращения.
Исполнитель — не новая глобальная роль, а назначенный пользователь заявки.

| Действие | Владелец | Координатор | Сотрудник |
|---|---|---|---|
| Создать обращение от своего имени | Да | Да | Да |
| Список/карточка/история | Все в своём пространстве | Все в своём пространстве | Только свои и назначенные ему |
| Назначить/снять исполнителя | Да | Да | Нет |
| Перевести в работу/выполнить | Да | Да | Только назначенную ему |
| Пригласить/отозвать сотрудника | Да | Да, только employee | Нет |
| Назначить/снять координатора | Да | Нет | Нет |
| Читать проект, Vault, чужое пространство | По прежним редакторским правам | Роль обращений ничего не добавляет | Роль обращений ничего не добавляет |

Сервер фильтрует список, карточку, историю и счётчики по одному правилу.
Фильтр пользователя лишь сужает разрешённое. Чужая запись/недопущенный участник
— 404; сессии нет — 401; запрет операции над видимой записью — 403.
Проверка сессии и допуска повторяется после чтения тела и перед записью.
Назначать можно только активного участника обращений этого пространства
(включая владельца); чужой ID не раскрывает информацию о другом аккаунте.

Отзыв допуска сразу запрещает чтение/изменения и Telegram-действия; историю
не уничтожает. Назначенные отозванному сотруднику заявки видит координатор
и переназначает явно. Удаление пользователя не должно каскадно удалить заявки.

## 3. Модель данных и переходы (контракт 12B)

- `request_members`: пространство, существующий user_id, роль, признак отзыва,
  даты. Уникальность (workspace_id, user_id); без записи в workspace_members.
- `requests`: непрозрачный id, номер внутри пространства, workspace_id,
  author_user_id, assignee_user_id (опционально), текст, status, revision,
  created_at, updated_at, completed_at (опционально). Номер не является секретом
  или разрешением; время UTC формирует сервер, текст 1–4000 символов после trim.
- `request_events`: неизменяемая история создания/назначения/переходов с actor,
  датой и старым/новым состоянием. Без копии полного текста в каждом событии.
- `request_commands`: ключ идемпотентности, область workspace+actor,
  отпечаток команды и её результат; запись атомарна с созданием заявки.
- В 12D: scoped Telegram-привязки, входящая очередь и задания уведомлений.
  Их схема не заменяет таблицы схем/исполнений и не встраивается в JSON проекта.

Переходы: `new → in_progress → done`. Обратные переходы, редактирование текста
и удаление через обычное API не входят в первый пилот. Для перехода в работу
нужен активный исполнитель. После done назначение/статус неизменяемы.
Повтор текущего состояния — допустимый no-op только после проверки прав
и совпадения expectedRevision; история/уведомления не дублируются.

Ревизия — случайная метка 32 hex. PATCH требует expectedRevision: отсутствует
— 428, неверный формат — 400, устарела — 409 без чужих данных. UPDATE с условием
и событие истории выполняются одной транзакцией; конфликт ничего не пишет.
Создание + номер + событие + идемпотентный результат — тоже одна транзакция.

## 4. Целевой API (ещё не зарегистрирован)

| Метод/путь | Назначение |
|---|---|
| GET `/api/request-workspaces` | Пространства, где разрешены обращения; без доступа к проектам/секретам |
| GET `/api/workspaces/:wsId/requests` | Разрешённые заявки, limit 1–100, cursor, фильтр статуса |
| POST `/api/workspaces/:wsId/requests` | `{ text, idempotencyKey }`; автор из сессии, статус/даты/номер — сервер |
| GET `/api/workspaces/:wsId/requests/:id` | Карточка с revision |
| PATCH `/api/workspaces/:wsId/requests/:id` | Одно действие: назначение либо смена статуса + expectedRevision |
| GET `/api/workspaces/:wsId/requests/:id/events` | Разрешённая история с пагинацией |

Ключ создания — UUID клиента. Повтор того же ключа с тем же содержимым
возвращает тот же результат; с иным содержимым — 409. Ключ не заменяет
проверку текущего допуска. Не принимать author/workspace/role из JSON как
доказательство полномочий; неизвестные поля команд отклонять.
Полные контракты управления допуском/привязкой понадобятся до подключения
пользователей в 12C/D; на 12B покрыть матрицу подготовленными серверными fixtures.

## 5. Telegram и обработка сбоев (требования 12D)

Для пилота — только личный чат с ботом. Допуск в команду и привязка Telegram
раздельны. Приглашение в обращения принимается существующим аккаунтом;
случайный одноразовый токен ограничен пространством/ролью/сроком, в БД только
дайджест. Координатор не может выпустить приглашение координатора.

Привязка Telegram: короткоживущий одноразовый код из авторизованного кабинета,
его отправка боту, затем подтверждение кандидата тем же аккаунтом в кабинете.
До подтверждения нет допуска. Username только для отображения, не идентичность.
Уникальность bot_id + telegram_user_id; бот обязан принадлежать пространству.
Отзыв участника/привязки проверяется заново при каждом сообщении/callback.

До ответа 200 поддерживаемое событие должно попасть в долговременный inbox
с UNIQUE(bot_id, update_id). edited_message не создаёт заявку. Создание заявки,
история и задание уведомления атомарны; повтор обработки возвращает исходный
результат. Идентичность автора берётся из серверного конверта/привязки,
не из конфигурации блока, текста сообщения или входного провода схемы.

Сбой до записи inbox — повторяемый HTTP-сбой, не «успешный приём».
Перегрузка откладывает обработку, не удаляет событие. Внешняя отправка выполняется
после транзакции. У уведомлений отдельное состояние; ошибка не меняет заявку.
Таймаут после возможной отправки — `uncertain`: нельзя обещать отсутствие
дублей при повторе, ручной повтор должен предупреждать об этом.
Автоматические повторы разрешены только для однозначно повторяемых отказов
с ограничением попыток/задержкой; точный контракт транспорта — перед 12D.

Операции конструктора обращаются к одному серверному сервису заявок через
ограниченный адаптер runtime. Он проверяет actor/scope и идемпотентность,
не доверяет user_id/workspace_id из схемы. В симуляторе отдельный временный
адаптер или явная недоступность — никогда не HTTP-запись боевой заявки.
До боевого включения исключить текст обращений из общих сводок выполнения.

## 6. Приёмка и порядок следующей реализации

**12A завершён как аудит/контракт.** Следующий шаг — 12B: новая миграция,
сервис доступа/переходов/создания, затем маршруты. Минимальный набор тестов:

1. Миграции на пустой БД и поверх 012, сохранность проектов/версий/секретов.
2. Каждая клетка матрицы, прямые запросы к чужим ID, неверный исполнитель.
3. Сотрудник обращений не получает доступа к проектам/секретам.
4. Повтор создания/параллельные ключи, разные команды с одним ключом.
5. CAS, атомарная история, no-op, rollback ошибки, сохранность после рестарта.
6. Отзыв допуска/сессии во время запроса, отсутствие утечек в списке/истории.
7. Затем 12C/D: сценарии UI и Telegram, таймауты/повторы/перегрузка,
   отдельный симулятор и запрещённые callback, политика журналирования.

Времена хранения/удаления, конкретная команда и согласие на реальные данные
остаются условиями пилота, а не придуманными результатами. VPS и настоящий бот
не затронуты. Оболочки остальных разделов не расширяют scope плана 12.
