# 06 — Этап 5 (продуктовый): Backend и превращение в работающий продукт

**Статус: подэтапы 5.1–5.11 завершены (2026-09-14); продакшн не развёрнут.** Документ соответствует «ЭТАПУ №5»
продуктового задания. Процессы разработки и деплоя по-прежнему описаны в
[05-DEVELOPMENT-DEPLOY.md](05-DEVELOPMENT-DEPLOY.md) (они действуют всегда).

## Цель

Последовательно превратить NODEZZLE из качественного frontend-фундамента
в реально работающий продукт: серверный фундамент → аккаунты → проекты
на сервере → секреты → реальный Telegram → Draft/Live и публикации →
лимиты и аудит → продакшн-готовность.

**Не делать всё одним изменением.** Каждый подэтап — небольшой,
с тестами и Definition of Done; после каждого — проверки, документы,
коммит, пуш.

## Архитектурные решения Этапа 5

1. **Ноль новых рантайм-зависимостей.** Сервер — на встроенных модулях
   Node ≥ 22.18: `node:http` (API), `node:sqlite` (БД, файл),
   `node:crypto` (scrypt-пароли, HMAC-сессии, AES-256-GCM для секретов),
   запуск TypeScript встроенным type-stripping (явные расширения `.ts`
   в импортах). Единственная добавленная зависимость — `@types/node`
   (devDependency, типы).
2. **Единый формат.** Сервер валидирует документы проектов той же
   Zod-схемой `src/core/project/schema.ts` — клиент и сервер понимают
   один формат.
3. **БД — только через миграции**: нумерованные идемпотентные `.sql`-файлы
   `server/migrations/`, таблица `schema_migrations`, только вперёд
   ([DATABASE.md](../DATABASE.md) §2.2).
4. **Секреты — только на сервере**: значения шифруются (AES-256-GCM),
   клиенту не возвращаются, в логи не пишутся; в схемах — только
   `secret_id` ([SECURITY.md](../SECURITY.md) §3.2).
5. **Порты**: локальный API — `127.0.0.1:4210` по умолчанию
   (переменная `NODEZZLE_API_PORT`). Порты 3000/3001 запрещены всегда
   ([RULES.md](RULES.md), правило 16).
6. **Русский интерфейс сохраняется**; технические идентификаторы API —
   английские.

## Подэтапы

| Подэтап | Цель |
|---|---|
| 5.1 | Каркас сервера: конфиг окружения, централизованные ошибки, роутер, `/api/health`, слой БД + мигратор, первая миграция (`users`) |
| 5.2 | Аккаунты: регистрация, вход, выход; scrypt-пароли, сессии (HttpOnly-cookie, HMAC), rate-limit логина |
| 5.3 | Проекты на сервере: рабочие пространства, CRUD проектов (валидация форматом), серверное сохранение |
| 5.4 | Версии проектов: снапшоты, список, восстановление; семантика Draft |
| 5.5 | Secrets Vault: шифрование, `secret_id`, аудит доступа; таблица `secrets` |
| 5.6 | Валидация публикации: порты, модели, рекурсия, обязательные входы; публикация = иммутабельная версия = LIVE |
| 5.7 | Production Runtime: очередь выполнений, лимиты (шаги, таймаут, размер, глубина моделей), журнал выполнений |
| 5.8 | Реальный Telegram: подключение бота (токен → секрет), webhook → LIVE-версия → действия; симулятор остаётся отдельным |
| 5.9 | История выполнений, аудит-журнал, лимиты пользователей |
| 5.10 | Локальный запуск владельца: `start-nodezzle.bat`, инструкция; подготовка к деплою (деплой — по отдельной команде) |
| 5.11 | Академия: движок уроков, интерфейс, песочница, оверлей, курс, справочник, помощь, онбординг и QA (A–H) |

Состав может уточняться по ходу — изменения фиксируются здесь и в
[STATUS.md](STATUS.md).

## Definition of Done подэтапа

1. Реализация небольшая и законченная.
2. `npm run typecheck`, `npm test`, `npm run build` — зелёные
   (включая серверные тесты).
3. Обновлены: `STATUS.md`, `IMPLEMENTATION_MATRIX.md`, `ROADMAP.md`,
   связанные документы (`DATABASE.md`, `SECURITY.md`, …), `CHANGELOG.md`.
4. Коммит + пуш. Только после пуша — следующий подэтап.

## Честность статусов

Серверные системы отмечаются в документах только фактическими статусами
(СПЕЦИФИКАЦИЯ / ЗАПЛАНИРОВАНО / ПРОТОТИП / РЕАЛИЗОВАНО / ПОКРЫТО ТЕСТАМИ /
ПРОДАКШН-ГОТОВО). До отдельной команды владельца продакшн-статус
не ставится ничему; деплой на VPS в Этапе 5 не выполняется.
