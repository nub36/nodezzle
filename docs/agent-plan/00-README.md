# 00 — Постоянный план разработки NODEZZLE

Этот каталог — **долговременная память проекта для всех AI-агентов**.

## Почему это существует

NODEZZLE разрабатывается через несколько AI-сессий Arena. Сессии могут завершаться,
зависать или достигать лимита контекста. Поэтому:

- **НЕЛЬЗЯ** хранить основной план разработки только в чатах.
- GitHub содержит **весь план проекта** и **точное место, где остановилась разработка**.
- Если чат утерян — работа продолжается по этому каталогу и по Git.

## Как развивается NODEZZLE

NODEZZLE развивается **по последовательным этапам**. Каждый этап зафиксирован
отдельным документом:

| Документ | Этап | Содержание |
|---|---|---|
| [01-FOUNDATION.md](01-FOUNDATION.md) | Этап 1 — Фундамент (Промпт №1) | Концепция, стек, ядро, Canvas, формат проекта. **Выполнен** (зафиксирован в коммите `a1b0c20`). |
| [02-CANVAS-UI.md](02-CANVAS-UI.md) | Этап 2 — Canvas UI (Промпт №2) | Библиотека, тулбар, живые блоки, Quick Insert, Inspector, модели, Drill Down, превью/отладка. |
| [03-MASTER-SPEC.md](03-MASTER-SPEC.md) | Этап 3 — Мастер-спецификация (Промпт №3) | Полная проектная память: мастер-спека, страницы, системы. |
| [04-BLOCK-LIBRARY.md](04-BLOCK-LIBRARY.md) | Этап 4 — Библиотека блоков (Промпт №4) | 16 категорий × 10+ блоков = 160+ определений, масштабируемость до 1000+. |
| [05-DEVELOPMENT-DEPLOY.md](05-DEVELOPMENT-DEPLOY.md) | Процесс разработки и деплоя (действует всегда) | Процесс работы, ROADMAP, VPS-деплой, безопасность секретов. |
| [06-BACKEND-PRODUCT.md](06-BACKEND-PRODUCT.md) | Этап 5 (продуктовый) — Backend и продукт (Промпт №6) | Серверный фундамент, аккаунты, БД, секреты, Telegram, Draft/Live, лимиты. |
| [07-COMPACT-LEARNING.md](07-COMPACT-LEARNING.md) | Развитие UX и обучения | Компактные детали, учебные материалы, браузерный QA. |
| [08-CANVAS-UX.md](08-CANVAS-UX.md) | Продолжение UX редактора | Копирование/дублирование без наложений, панели на узких экранах. |
| [09-TELEGRAM-WEB.md](09-TELEGRAM-WEB.md) | Telegram и Web | Завершён в описанном объёме: адресные события, веб-элементы, Telegram callback/клавиатура. |
| [10-SERVER-PROJECTS.md](10-SERVER-PROJECTS.md) | Серверное сохранение | Завершён в описанном объёме: копии, ревизии, серверный Canvas, резерв/конфликты и приёмка. |
| [11-NOVICE-CANVAS.md](11-NOVICE-CANVAS.md) | Редактор для новичка | Выполнен в описанном UX-объёме (0.5.49): 771 unit/integration + 108 E2E. Далее выбран план 12 — внутренние обращения. |
| [12-INTERNAL-REQUESTS.md](12-INTERNAL-REQUESTS.md) | Внутренние обращения команд | 12A: аудит/контракт завершён; далее 12B — серверные данные и API. Оболочка сайта 0.5.50 не заменяет бизнес-логику. |
| [STATUS.md](STATUS.md) | — | **Точное место, где остановилась разработка.** Обновляется после каждого подэтапа. |
| [RULES.md](RULES.md) | — | Обязательные правила. Нарушать нельзя. |

Этап может делиться на подэтапы (например, Этап 2 — на пункты A–I). Не обязательно
реализовывать весь этап одним махом — но каждый завершённый подэтап фиксируется
в [STATUS.md](STATUS.md) и в Git (см. [05-DEVELOPMENT-DEPLOY.md](05-DEVELOPMENT-DEPLOY.md)).

## Обязательный порядок действий агента ПЕРЕД работой

**ПЕРЕД ЛЮБОЙ РАЗРАБОТКОЙ** агент обязан:

1. Прочитать `/AGENTS.md`.
2. Прочитать [docs/agent-plan/00-README.md](00-README.md) (этот файл).
3. Прочитать [docs/agent-plan/STATUS.md](STATUS.md).
4. Прочитать документ **текущего этапа** (указан в STATUS.md).
5. Прочитать связанную техническую документацию (`docs/` — ARCHITECTURE, BLOCKS,
   MODELS, TELEGRAM, WEB, UI, PROJECT_FORMAT, ROADMAP, DECISIONS, IDEAS).
6. Выполнить `git status` и `git log --oneline -10`, сверить фактическое состояние
   репозитория со STATUS.md.
7. Только затем продолжать разработку.

## Запреты

- **Не начинать выполненный этап заново.** Если этап отмечен как выполненный —
  он выполнен. Проверяй факт по Git (`git log`, файлы, тесты), а не по ощущениям.
- Если фактический Git **расходится** со STATUS.md — верить Git, затем обновить
  STATUS.md и сообщить владельцу о расхождении.
- Не принимать решений, противоречащих [RULES.md](RULES.md).
