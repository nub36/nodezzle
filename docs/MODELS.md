# NODEZZLE — Модели

Модель — **главная функция NODEZZLE**: способ собирать блоки в переиспользуемые детали.

## Что такое модель

Модель = **публичный контракт** + **внутренняя схема**:

```
StoredModel = {
  id, name, version,
  contract: {
    inputs:  [{ id, name, type, description?, required? }],
    outputs: [{ id, name, type, description?, required? }],
    error?:  { id, name, type },
    events?: [...]
  },
  canvas: <CanvasDocument>,   // обычная схема из обычных блоков
  updatedAt
}
```

Пример — **ORDER MODEL**:

Внутри: `Input → Validation → Logic → Processing → Output`.
Внешний контракт:

```
INPUT:  user_id: Number, product_id: Number, quantity: Number
OUTPUT: order_id: Number, price: Number, status: Text
ERROR:  error_message: Text
```

После создания модель **становится новой деталью**: её можно ставить на другие схемы блоком «Вызов модели».

## Иерархия

```
ATOMIC BLOCK → MODULE → MODEL → MODEL OF MODELS → APPLICATION
```

**Модель внутри модели — поддерживается** (реализовано на Этапе 0): вызов модели рекурсивен, лимиты runtime (бюджет шагов, исполнение узлов) применяются ко всему дереву вызовов.

## Ключевые блоки моделей

| Блок | Роль |
|---|---|
| **Вход модели** (`core.input`, `entry`) | Берёт значение из `contract.inputs` по `config.portId` |
| **Выход модели** (`core.output`) | Пишет значение в `contract.outputs` по `config.portId` |
| **Вызов модели** (`models.call`) | Вызывает модель по `config.modelId`: входной объект маппится на контракт, результат — объект со всеми OUTPUT |

## Взаимодействие моделей (механизмы)

| Механизм | Статус | Как |
|---|---|---|
| **INPUT/OUTPUT (контракт)** | ✅ | Публичные порты модели |
| **CALL MODEL** | ✅ | `models.call` + рекурсивное `executeModel` |
| **EVENT (SEND/RECEIVE)** | ⏳ | Блоки зарезервированы (`event.send/receive`), этап 5 |
| **REQUEST/RESPONSE** | ⏳ | На базе CALL MODEL + error-контракта, этап 5 |
| **SHARED MEMORY** | ⏳ | `memory.shared` + `runtime.memory` (задел в runtime есть), этап 5 |

## Drill Down

Пользователь открывает модель как отдельный Canvas и работает внутри:

```
Проект > Telegram > Заказы > Оплата
```

На Этапе 0 модель хранится в проекте и вызывается; **Drill Down-редактор** (открыть модель внутри UI, breadcrumb-навигация, сохранение viewport модели) — этап 2 ROADMAP. Механизм (canvas модели = обычный CanvasDocument, формат `CanvasDocument` универсален) уже готов.

## Как создаётся модель (план UX)

1. Выделить детали (или создать новые) → «Сохранить как модель».
2. Определить контракт: какие INPUT (имя, тип, required), какие OUTPUT, ERROR.
3. Связать `Вход модели`/`Выход модели` с внутренними блоками.
4. Модель появляется в библиотеке («Мои модели») и становится доступной для «Вызова модели».

На Этапе 0 модель создавалась демо-проектом; с Этапа 2 (подэтап G, v0.2.8)
модель создаётся прямо из Canvas: выделить детали → «Создать модель из
выделенного» (контекстное меню) → диалог показывает автоматически
определённый контракт (граничные связи становятся ВХОД/ВЫХОД/ОШИБКА) →
выделение заменяется «Вызовом модели», граничные значения идут через
конвертеры «В объект»/«Из объекта». Ограничения первой версии: не более
одного внешнего входа, без внешних связей-событий и триггеров внутри
выделения; многопортовые контракты появятся вместе с динамическими портами.

## Конventions

- `version` модели инкрементируется при изменении контракта (задел под совместимость версий).
- id контракта — технические (англ.); `name` — человекочитаемое (русское).
- Контракт — часть формата проекта и проверяется Zod-схемой.
- Ошибка внутри модели → ERROR-выход модели (error-порт контракта) → ошибка вызывающего блока.


## Ошибки вложенного исполнения (0.5.32)

`executeModel` проверяет итог внутреннего `executeCanvas`. Неуспех
(error, waiting, stopped) не превращается в успешный пустой результат:
код ошибки передаётся обработчику `models.call`, который возвращает
ошибку, а не порт `result`. Это действует и через несколько уровней.
Остановка дополнительно обрабатывается общим токеном отмены runtime.

Успешная модель с пустым внешним контрактом возвращает `{}` — это
нормально, например, для цепочки «Текст → Лог» без внешних связей.
Внутренние журналы сохраняются. Это не транзакция: уже совершённые
побочные эффекты не откатываются. Тесты проверяют ошибочное преобразование,
вложенный вызов, неподходящий триггер и допустимый пустой результат.

Браузерный урок проверяет извлечение двух деталей через Ctrl/Cmd,
сохранение модели после F5, фактический внутренний лог, двойной клик
для спуска, ошибку внутри и исправление. Формат проекта не менялся.
