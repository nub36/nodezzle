# NODEZZLE — Telegram Layer

Telegram — первое основное направление NODEZZLE. Слой построен **поверх общего ядра**: Telegram-блоки — обычные Block Definitions с категорией `telegram`; транспорт (Bot API) изолирован в runtime-адаптере `runtime.telegram`.

## Блоки Telegram (Этап 0)

| Блок | ID | Тип | Порты |
|---|---|---|---|
| Получено сообщение | `telegram.message_received` | триггер | → Текст, ID пользователя, ID чата, Имя, TelegramMessage |
| Команда | `telegram.command` | триггер (config: `command`, напр. `/start`) | → Команда, Аргументы, ID пользователя, ID чата |
| Отправить сообщение | `telegram.send_message` | действие | ← Текст, ID чата → ID сообщения (+Error) |
| Отправить фото | `telegram.send_photo` | действие | ← Фото (image), Подпись, ID чата → ID сообщения (+Error) |

Callback Query и Answer Callback реализованы в 09C1 ниже. Конфигурация бота и серверный транспорт существуют (5.8). Inline Keyboard реализована в 09C2 ниже; Get User, Get Chat, Edit Message, Send Document, Send File, Delete Message пока не реализованы как блоки.

## События и порты

Telegram-событие потенциально содержит:

```
message, text, user, user_id, username, chat, chat_id,
photo, document, voice, video, location, callback, command
```

Не всё отдаётся сразу — **архитектура позволяет расширять набор портов** без изменения ядра: порт = запись в `PortDefinition` + i18n-ключ. Правило: порты события — с типами (`telegram_message`, `text`, `number`, `user`, `image`…), чтобы умные соединения работали.

## Пример схемы (демо-проект)

```
Получено сообщение ──→ В объект (text) ──→ Вызов модели «Приветствие»
      │                                            │
      │ (chat_id)                     (result: reply)
      │                                            ↓
Отправить сообщение ←── Из объекта (reply) ←──────┘
```

Модель «Приветствие» (контракт: `text → reply`):

```
Вход (text) → Условие (содержит «привет»?) → Выход (reply)
```

Это демо загружается с Dashboard: «Загрузить пример: Telegram-бот». Запуск — через Симулятор (Debug-панель): payload `{text, chat_id, user_id, command?}`.

## Как запускается схема (сейчас и в будущем)

**Сейчас (Этап 0, симуляция):**
- Отправки (`send_message`, `send_photo`) идут в **outbox** — виртуальный журнал, видимый в Debug-панели («Чат Telegram») и демо-чате главной страницы.
- Входящие события создаёт Симулятор (настраиваемый payload).
- Реального Telegram-токена во frontend **нет и не будет**.

**Реальная интеграция (Этап 5, подэтап 5.8 — завершён 2026-09-14):**
- Токен бота вводится владельцем через защищённый эндпоинт и хранится
  **только в Secrets Vault** (AES-256-GCM); бот привязывается к
  пространству/проекту ссылкой `secret_id` — в Project JSON токена
  нет и не будет.
- Конфигурация бота: `POST/GET/PATCH/DELETE
  /api/workspaces/:id/telegram-bots` (подэтап 5.8A). Токен не
  возвращается ни в одном ответе; чужой `secret_id` использовать
  нельзя (404).
- Вебхук `POST /api/telegram/webhook/:path` (подэтап 5.8B): путь —
  случайные 32 байта; лимит частоты по «адрес + путь»; лимит размера
  тела; строгая валидация обновления схемой; нормализация в событие
  NODEZZLE (`source: 'telegram'`, текст/команда/пользователь/чат).
  Запуск **только опубликованной (LIVE) версии** (подэтап 5.8D):
  обновление → сервер находит бота по пути → берёт токен из Secrets
  Vault → исполняет LIVE-снапшот с лимитами рантайма → исходящие
  сообщения отправляются транспортом; черновик никогда не
  исполняется вебхуком.
- Транспорт Bot API `server/src/telegram/api.ts` (подэтап 5.8C):
  `getMe`, `sendMessage`, `sendPhoto`, `editMessageText`,
  `deleteMessage`, `answerCallbackQuery`; таймаут (по умолчанию 10 с),
  нормализация ошибок в `TelegramApiError`; базовый адрес фиксирован
  (официальный домен) — нет SSRF; токен знает только транспорт и не
  пишет его ни в ошибки, ни в журнал. Тесты — только на моках.
- Симулятор остаётся отдельным контуром: работает без токена, без
  бота, локально; вебхук-контур его не трогает.
- Панель подключения на Панели управления (подэтап 5.8E, русский
  интерфейс): токен вводится один раз в поле пароля и уходит только
  на сервер; после подключения показываются имя секрета, имя/ник бота
  и статус; действия — Подключить / Заменить токен / Отключить.
  Токен не сохраняется в браузере (`localStorage`) и не попадает в
  файл проекта.
- Управление вебхуком (подэтап 5.8F): `POST/GET/DELETE
  /api/workspaces/:id/telegram-bots/:botId/webhook` — регистрация,
  проверка статуса и удаление вебхука через транспорт. Регистрация
  выполняется только при публичном HTTPS-адресе (локальные, служебные
  адреса и `http://` отклоняются до обращения к Telegram); секретный
  путь вебхука одновременно передаётся как секретный заголовок
  вебхука. Локальная разработка работает без вебхука и без токена.

## Безопасность

- **Токен — только в Secrets Vault** (подэтап 5.8): шифруется на
  сервере; бот хранит ссылку `secret_id`; значение не возвращается
  клиенту, не пишется в логи и не попадает в Project JSON.
- Чужой `secret_id` использовать нельзя: секрет обязан принадлежать
  тому же рабочему пространству, иначе 404.
- Вебхук защищён случайным публичным путём (`webhook_path`, 32 байта),
  входящие обновления валидируются, размер ограничен, эндпоинт
  под лимитом частоты (подэтапы 5.8B).
- Платформенные правила: никаких реальных credentials в UI, в формате
  проекта, в логах. Входящие сообщения проходят валидацию, payload
  нормализуется в события NODEZZLE.


## Callback обычного сообщения (09C1, 0.5.44)

Аудит 09C: серверные webhook/LIVE/Vault/Bot API уже существовали, но
callback не нормализовался, а callback_query/answer_callback были planned.
Эти две детали реализованы в C1. Конструктор inline-клавиатуры и нажатия
в превью добавлены отдельно в C2 ниже. Inline-клавиатура
под обычным сообщением не равна Telegram inline-mode (`inline_query`).

### Событие и маршрутизация

- `telegram.callback_query` («Нажата кнопка») сохраняет data:text,
  message_id:number, user_id:number, chat_id:number; добавлен выход
  callback_id:text («ID callback-запроса»).
- Настройка callbackDataFilter: точное сравнение, без обрезки пробелов
  и изменения регистра; пустая строка принимает все допустимые callbacks.
  Некорректный фильтр не совпадает ни с чем. Два одинаковых/пустых фильтра
  могут запустить обе цепочки — это не автоматическое разделение адресатов.
- Нормализованный payload:
  `{source:'telegram',telegram:{event:'callback_query',callback_id:'cb-1',
  data:'confirm',message_id:10,user_id:42,chat_id:1000,text:''}}`.
  Username переносится, если есть. user_id — **нажавший кнопку**, не автор
  сообщения бота. Текст исходного сообщения/команда/raw не копируются.
- callback_id: непустая строка ≤256 UTF-16 единиц, без пробелов/управляющих
  символов (локальный защитный предел). data: 1–64 **байта UTF-8**, не символа:
  32 буквы «я» допустимы, 33 — нет; 16 emoji по 4 байта допустимы, 17 — нет.
  user_id/message_id — безопасные целые >0; chat_id — безопасное целое ≠0,
  отрицательный ID группы допустим. Нет искусственного чата 0.
- Web/model и обычное сообщение не запускают callback. Callback не запускает
  message_received/command, даже если недоверенный payload содержит command.
  Старые Telegram payload без event сохраняют поведение сообщений/команд.
- Вебхук проверяет форму callback_query, отбрасывает дополнительные поля.
  Несколько поддерживаемых типов в одном Update отклоняются как неоднозначные.
  Inline-mode без message, игры, callback без data и недоступное сообщение
  (date=0) пока игнорируются. Остальной обработчик сообщений не переписан.

### Ответ на нажатие — не сообщение в чате

`telegram.answer_callback` сохраняет text/show_alert → ok/error;
добавлен вход callback_id:text. Вход ID приоритетен; только undefined
использует ID текущего **проверенного** callback-события. null/пустая строка
не означают fallback. Явный ID можно передать по проводу через модель;
получать произвольные ID из константы для реального бота не следует.

Настройки text='' и show_alert=false; подключённые входы приоритетнее.
Текст — строка до 200 Unicode-кодовых точек, включая пустую. show_alert —
именно boolean, не строка «false». В инспекторе это checkbox «Показать окно
Telegram». Ошибка данных — ERR_TELEGRAM_CALLBACK. Старый пользовательский
адаптер без answerCallback получает ERR_TELEGRAM_CALLBACK_ADAPTER.

Runtime помещает отдельное действие в outbox:
`{id,at,kind:'callback_answer',callbackQueryId,text,showAlert}` — без chatId.
Серверный обработчик отправляет его через существующий answerCallbackQuery
с callback_query_id/text/show_alert, а **не** через sendMessage. Остальные
элементы outbox сохраняют прежнее поведение. Вкладки «Чат Telegram» и
«Телефон» показывают локальное уведомление с явной пометкой симуляции;
оно не является пузырём сообщения или настоящим окном Telegram.

**ok=true означает только добавление в outbox.** LIVE-обработчик доставляет
действия после выполнения схемы, поэтому поздний/повторный ответ Telegram
может отклонить. Нет мгновенного автоответа, повторов, дедупликации или
подтверждения доставки в порте ok. Журнал выполнения создаётся до доставки
и не доказывает её успех. Не ставьте долгие действия перед подтверждением.
Фото в старом LIVE-обработчике по-прежнему уходит подписью как текстом;
реальная отправка фото из outbox не исправлялась этим подэтапом.

### Практика: подтвердить кнопку без токена

1. Создайте проект, включите «Все» в библиотеке. Добавьте «Нажата кнопка»
   (`telegram.callback_query`), задайте фильтр данных `confirm`.
2. Добавьте «Ответ на кнопку» (`telegram.answer_callback`). Соедините выход
   «ID callback-запроса» первого блока с одноимённым входом второго.
3. В свойствах ответа задайте текст «Подтверждено» и включите «Показать
   окно Telegram». Пустой текст и выключенный checkbox тоже допустимы.
4. В «Симуляторе» выберите Telegram → «Нажатие inline-кнопки». Данные —
   `confirm`, ID запроса — `sim-callback-1`, ID сообщения — `1`,
   пользователя — `42`, чата — `1000`. Это тестовые данные, не токен.
5. Нажмите «Запустить». Во вкладке «Порты» проверьте данные/ID и ok=true;
   в «Чате Telegram»/«Телефоне» — отдельное подтверждение с пометкой симуляции.
6. Измените данные на `cancel`: фильтр не совпадёт, ответа не будет.
   Верните `confirm` — ответ снова появится. Для второй цепочки задайте
   отдельному callback-блоку фильтр `cancel`.
7. Переключите событие на «Сообщение / команда»: callback пропущен. Ранее
   введённая команда не переносится в callback и не запускает её обработчик.
8. F5 сохраняет схему/настройки, но не поля симулятора и не outbox. Выберите
   callback-режим заново. При входе в текущие уроки также включается режим
   сообщения; callback не засчитывается как учебная отправка сообщения.

Для боевого callback нужен уже опубликованный LIVE-проект и существующий
контур бота. Тесты этой версии используют только моки; реальный бот и
деплой не проверялись. Не вводите токен в Canvas или callback-данные.

Проверено: 31 новый unit/integration + 4 E2E; всего **641 + 79**, типы и
сборка успешны. Web B1–B5, старые Telegram-сценарии и все 12 уроков сохранены.


## Inline-клавиатура и нажатия в превью (09C2, 0.5.45)

Ограничение C1 о конструкторе клавиатуры снято. Реализована новая деталь
`telegram.inline_keyboard`, передача разметки через `send_message` и клики
в Чате/Телефоне. Это callback-клавиатура **под обычным текстовым сообщением**,
не Telegram inline-mode и не URL/WebApp-кнопки.

### Контракт разметки и отправки

- Конструктор: rows:array → keyboard:object (+error). Настройка rows — JSON
  рядов; по умолчанию одна кнопка «Подтвердить» с callback_data=confirm.
  Вход rows приоритетнее настройки. JSON разбирается только из настройки;
  строка по проводу, null, битый JSON и пустые ряды недопустимы.
- Выход — `{inline_keyboard:[[{text:'Подтвердить',callback_data:'confirm'}]]}`.
  Объект создаётся заново. Только эти ключи: дополнительные атрибуты,
  URL/pay/WebApp/game/login и смешанные действия отвергаются, не игнорируются.
- Локальные лимиты: 1–8 рядов, 1–8 кнопок в ряду, ≤32 всего. Подпись —
  1–64 Unicode-кодовых точки, не только пробелы. callback_data — прежние
  1–64 байта UTF-8 C1. Порядок рядов и кнопок сохранён, HTML остаётся текстом.
  Это поддерживаемое подмножество NODEZZLE, не полный набор возможностей API.
- У `telegram.send_message` добавлен необязательный вход keyboard:object.
  Без провода сохраняется прежняя отправка без reply_markup. С клавиатурой
  chat_id должен быть безопасным целым ≠0. Невалидная разметка отменяет
  отправку целиком с ERR_TELEGRAM_KEYBOARD — нет частичного списка кнопок.
- Ошибка подключённого источника **не равна отсутствию клавиатуры**.
  NodeExecutionContext получил необязательные connectedInputs (имена входов
  с проводами). Конструктор/отправка отказывают при недоставленном значении
  подключённых rows/keyboard, вместо молчаливого fallback. Сами правила
  планирования графа не изменялись, остальные обработчики совместимы.
- Runtime переносит разметку в текстовую запись outbox. LIVE-handler передаёт
  её существующему sendMessage; транспорт повторно проверяет и сериализует
  как reply_markup. Старое тело sendMessage без клавиатуры неизменно.

### Превью и идентификаторы

Общий контрол в «Чате Telegram»/«Телефоне» рисует настоящие кнопки (мышь,
клавиатурный Enter). Клиент не обращается к Telegram API. Клик передаёт
стору только уникальный **id записи outbox** и индексы ряда/кнопки. Подпись
не является адресом: одинаковые подписи могут иметь разные callback_data.
Стор повторно проверяет текущую запись, индексы, разметку, успешность запуска,
совпадение схемы/проекта/модели и userId симулятора. Кнопка disabled не
заменяет проверку в действии. Повторный быстрый вызов старой записи отклоняется.

Callback C1 получает data кнопки, chat_id именно исходящего сообщения
(не текущее поле чата симулятора), user_id из симулятора, новый синтетический
callback_id `sim-…` и message_id из записи. Порт message_id и поле messageId
outbox содержат прежние **локальные** номера 9001+; они не равны ID Telegram
и могут повторяться между запусками/вложенными исполнителями. Поэтому UI
адресуется UUID записи outbox, а не этим номером. На сервере реальные
message_id/callback_id приходят из webhook — подмены локальными нет.

Клик запускает схему и **заменяет outbox**, как обычный запуск: старая
клавиатура исчезает. История переписки не накапливается. Для повторной пробы
нажмите «Запустить» в режиме сообщения: поле режима симулятора не меняется
автоматически от клика. Если нужен ответ — подключите callback-цепочку C1.
Без подходящего триггера действуют обычные правила runtime, автоответа нет.

Неактуальная схема, error/running или неверный userId отключают кнопки с
пояснением. Перемещение/выделение узла не меняет данные схемы и не блокирует
клавиатуру. Переключение Чат ↔ Телефон сохраняет текущий результат; F5,
сброс и новый запуск очищают прежний outbox. Старые клавиатуры не сохраняются
в Project JSON. Клавиатура у фото и редактирование сообщений вне C2.

### Практика: «Да / Нет» без токена

1. Добавьте «Получено сообщение» и «Отправить сообщение». Соедините их
   одноимённые порты «Текст» и «ID чата».
2. В режиме библиотеки «Все» добавьте «Inline-клавиатура».
3. В «Ряды кнопок (JSON)» вставьте:
   `[[{"text":"Да","callback_data":"yes"},{"text":"Нет","callback_data":"no"}]]`.
4. Соедините выход «Клавиатура» конструктора с входом «Клавиатура» отправки.
   Для рядов по проводу можно использовать core.array → rows вместо настройки.
5. Добавьте «Нажата кнопка» (фильтр пока пустой) и «Ответ на кнопку».
   Соедините callback_id → callback_id и data («Данные») → text («Текст»).
6. В симуляторе выберите Telegram, «Сообщение / команда», текст «Выберите»,
   userId=42, chatId=1000. Нажмите «Запустить» и откройте «Чат Telegram».
7. Нажмите «Нет»: появится отдельное подтверждение «no», не новый пузырь
   сообщения. В «Портах» проверьте data, chat_id, message_id callback-блока.
8. Повторите «Запустить», перейдите в «Телефон» и нажмите «Да».
9. Измените JSON на `[[]]`: прежние кнопки отключатся, новый запуск не
   отправит сообщение без клавиатуры. Исправьте JSON и запустите снова.
10. Для разных действий используйте несколько callback-блоков с точными
    фильтрами yes/no. Фильтр не заменяет проверку полномочий/состояния заказа.

Проверки C2: 28 новых unit/integration + 3 E2E; весь набор **669 + 82**.
Включены реальные провода/клики/Enter, одинаковые подписи, отказ старых
результатов и двойных вызовов, безопасный текст, 390 px, F5, LIVE-разметка
и callback на моках. Все 12 уроков сохранены; урок «Порты» объясняет третий
необязательный вход отправки. ADR-026. Деплоя и проверки реального бота нет.


## Аудит для внутренних обращений (12A, 2026-09-15)

Обнаружены ограничения текущего пути: вебхук поглощает ошибку обработчика
и отвечает 200; перегрузка может завершить обработчик без исполнения;
external_event_id не уникален; отправка outbox не имеет долговременных
заданий/статусов доставки. Для message нормализация теряет тип чата/message_id
и не отделяет edited_message. Это не готовый надёжный приём заявок.

Дельта для 12D — [контракт 12A](agent-plan/12A-REQUEST-CONTRACT.md):
допуск/подтверждение Telegram-идентичности, серверный конверт источника,
долговременный inbox, транзакционная заявка/история/уведомление, отдельный
учёт неопределённой отправки и защита секретного заголовка. До реализации
пилот не объявляется готовым. Симулятор остаётся отдельным контуром.
