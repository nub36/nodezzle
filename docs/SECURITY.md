# SECURITY — Модель безопасности NODEZZLE

**Обновлено:** 2026-09-14 (Этап 3). Статусы разделов — по легенде
[MASTER_SPEC.md](MASTER_SPEC.md) §1. Сейчас продукт — локальное приложение
в браузере (хранилище LocalStorage), серверной части нет; документ фиксирует
действующие правила и целевую модель.

## 1. Действующие правила (РЕАЛИЗОВАНО / обязательны всегда)

### 1.1 Секреты в репозитории
- Репозиторий **публичный**. Запрещено коммитить: токены ботов, API-ключи,
  пароли, JWT/encryption secrets, production `.env`, приватные ключи
  ([RULES.md](agent-plan/RULES.md), правило 12).
- Допустим только `.env.example` с фиктивными значениями
  (пример: `NODEZZLE_TELEGRAM_BOT_TOKEN=123456:EXAMPLE-FIXTURE-DO-NOT-USE`).
- Перед каждым коммитом — проверка отсутствия секретов.

### 1.2 Секреты в продукте
- **Формат проекта не хранит секреты** — только ссылки на серверные секреты
  в будущем ([PROJECT_FORMAT.md](PROJECT_FORMAT.md), «Правила»).
- Реального Telegram-токена во frontend **нет и не будет**: весь транспорт —
  симуляция; будущий токен живёт только в `.env` сервера ([TELEGRAM.md](TELEGRAM.md)).
- Зарезервирован тип порта `secret` и цвет `#f87171` — будущие секреты
  маскируются в UI (маскирование — ЗАПЛАНИРОВАНО).

### 1.3 Валидация данных
- Все входящие данные проекта валидируются Zod (`tryParseProject`);
  мусорные/подменённые данные не попадают в рантайм.
- События симулятора нормализуются при сборке `TriggerPayload`
  (битый JSON веб-данных превращается в `{}`).

### 1.4 Инфраструктура (жёсткие ограничения)
- На VPS `89.125.24.50` работает **чужой сайт** (порты 3000/3001) — он
  неприкосновенен: не останавливать, не занимать порты, не трогать файлы,
  процессы и конфигурацию его обратного прокси ([05-DEVELOPMENT-DEPLOY.md](agent-plan/05-DEVELOPMENT-DEPLOY.md)).
- NODEZZLE разворачивается отдельно: собственный свободный порт, собственный
  обратный прокси + Let's Encrypt; домен `https://nodezzle.duckdns.org`.

## 2. Модель угроз и контрмеры

| Угроза | Статус | Контрмера |
|---|---|---|
| Утечка секретов через репозиторий | контрмера действует | правила §1.1, проверка перед коммитом |
| Секреты в схеме/проекте | контрмера действует | формат не хранит секреты; тип `secret` + будущее серверное хранилище |
| Повреждённые/подменённые данные проекта | контрмера действует | Zod-валидация при чтении; отклонение неизвестных `formatVersion` |
| XSS в пользовательских данных | частично | React экранирует вывод; i18n без интерполяции HTML; пользовательский ввод рендерится текстом |
| Вечные/тяжёлые схемы (зацикливание) | частично | рантайм имеет защиту от циклов и отмену; серверные лимиты — ЗАПЛАНИРОВАНО (§3) |
| Пользовательский JS (будущий блок `JS`) | ЗАПЛАНИРОВАНО | изоляция в sandbox/iframe (Этап 4, [WEB.md](WEB.md)) |
| Доступ к чужим проектам | ЗАПЛАНИРОВАНО | аутентификация и права (Этап 4); сейчас проекты локальные (браузер пользователя) |
| Компрометация токена бота | ЗАПЛАНИРОВАНО | токен только на сервере; ротация/отзыв — вместе с backend |

## 3. Целевая модель (ЗАПЛАНИРОВАНО)

### 3.1 Аутентификация и доступы
- Русские страницы: вход, регистрация, восстановление пароля (страница
  [pages/AUTH.md](pages/AUTH.md)).
- Модель доступа: пользователь → рабочее пространство → проекты
  (сущности — [DATABASE.md](DATABASE.md)). Общие правила для команды —
  экспериментальная идея ([IDEAS.md](IDEAS.md)).

### 3.2 Хранение секретов
- Секреты — только на сервере; в схемах хранится `secret_id`, а не значение.
- Маскирование значений в UI (вход/журнал), аудит доступа.

### 3.3 Изоляция исполнения
- Пользовательский код (будущие `JS`/`CSS`-блоки веб-слоя) исполняется в
  изолированном окружении (iframe/sandbox), без доступа к приложению.
- Серверное выполнение схем — с лимитами: время, число итераций, память,
  частота запусков (защита от «вечных» схем и злоупотреблений).

### 3.4 Транспорт
- Весь трафик по HTTPS; секреты — только в `.env` сервера; вебхуки
  подписываются/проверяются при появлении реального транспорта.

## 4. Чек-лист безопасности (для каждого изменения)

1. В коммите нет секретов (файлы окружения, токены, ключи, пароли)?
2. Новые пользовательские данные проходят валидацию (Zod/типизация)?
3. Пользовательский ввод не вставляется в разметку как HTML?
4. Изменение не касается чужого сайта на VPS и портов 3000/3001?
5. Документация обновлена, статусы честные (правило 7)?
