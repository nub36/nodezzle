# NODEZZLE — Архитектура системы

Документ описывает, **как устроено ядро NODEZZLE** (что реализовано на Этапе 0) и **как система будет расти** без переписывания. Обоснование выбора технологий — [DECISIONS.md](DECISIONS.md).

## 1. Принципы

1. **Ядро не знает о платформах.** Canvas, runtime, хранилище работают с абстрактными блоками. Telegram и Web — это просто наборы Block Definitions. Новая платформа (Discord и т.д. — если потребуется) = новый модуль блоков + регистрация, без изменения ядра.
2. **Данные описаны схемой.** Формат проекта валидируется Zod-схемой (Zod = единственный источник правды TS-типов). Сервер и клиент понимают один и тот же формат.
3. **Runtime — чистый TypeScript.** Движок выполнения не зависит от React: его покрывают unit-тесты, и тот же код в будущем сможет работать на сервере (деплой/исполнение схем, backend-Telegram).
4. **UI-строки — только через i18n.** Основная локаль ru-RU; добавление языка = новый JSON-словарь.
5. **Минимум зависимостей, максимум пользы.** Только проверенные библиотеки (см. DECISIONS.md).

## 3. Block Definition — контракт детали

```ts
interface BlockDefinition {
  id: string;            // 'telegram.send_message' (англ., устойчивый)
  labelKey: string;      // i18n-ключ: «Отправить сообщение»
  category: BlockCategory;
  trigger?: boolean;     // точка входа схемы (триггер платформы)
  entry?: boolean;       // точка входа ВНУТРИ модели («Вход модели»)
  available?: boolean;   // false = зарезервировано (скрыто из палитры)
  inputs:  PortDefinition[];
  outputs: PortDefinition[];
  defaults?: Record<string, unknown>;
  matches?: (payload, config) => boolean;  // применимость триггера
  runtime?: (ctx: NodeExecutionContext) => NodeHandlerResult;
}
```

- `runtime` — исполняемая логика блока (чистая функция + контекст).
- `matches` — решает, сработает ли триггер на конкретный payload (напр. «Команда /start» — только на `/start`).
- Конфигурация конкретного экземпляра хранится в `node.config` и редактируется в инспекторе (ConfigPanel).

Полное описание блоков и инструкция «как добавить блок» — [BLOCKS.md](BLOCKS.md).

## 4. Система типов портов

```
PortDefinition = { id, labelKey, kind: 'data'|'event'|'error', type: PortType }
```

**Совместимость (MVP-правила):**

| Источник (OUTPUT) | Приёмник (INPUT) | Разрешено |
|---|---|---|
| error | error | ✅ только error ↔ error |
| event | event | ✅ только event ↔ event |
| data `any` | data любой | ✅ |
| data `T` | data `T` | ✅ |
| data `T` | data `U ≠ T` | ❌ нужен Converter-блок |

Пользовательские типы регистрируются в `TypeRegistry` и декларируют, в какие базовые типы их можно лить. Типы — часть архитектуры: расширение набора не требует изменения движка (новые значения вида типа проходят как `PortType = string`).

## 5. Runtime — живое выполнение

`executeCanvas(canvasDocument, options) → ExecutionResult` (src/core/runtime/execute.ts).

**Механика:**

1. **Bootstrap.** Если в схеме есть триггеры/entry-блоки — запускаются только те, чей `matches` прошёл для payload (остальные помечаются `skipped`). Триггеров нет — стартуют «холодные» источники (блоки без соединённых входов: константы, значения).
2. **Готовность (push).** Узел выполняется, когда каждый его connected data-вход «удовлетворим»: значение доставлено, либо источник — pull-источник.
3. **Pull «холодных» источников.** Статический блок (напр. «Текст») выполняется on-demand, когда его значение впервые нужно соседу. Это разрешает естественные паттерны: `Команда → [Текст-константа] → Отправить сообщение`.
4. **Ветвление.** Условие/Switch пишут значения только в сработавшую ветку; молчащая ветка не затирает доставку портов (вход, к которому идут несколько соединений, получает значение первой сработавшей ветки).
5. **Ошибки.** Блок с ошибкой: статус ERROR + код (`errors.*` в i18n), распространяет сигнал по error-соединениям; данные на data-выходы не уходят.
6. **Защита от циклов.** Бюджет шагов (500) + лимит исполнений узла (25) → `ERR_CYCLE`.
7. **Отмена.** `cancel.cancelled` → схема завершается `STOPPED` (ERR_CANCELLED).
8. **Модели.** `models.call` → `runtime.executeModel(modelId, inputs)` → рекурсивный `executeCanvas` схемы модели с контрактом (вход: маппинг payload → `contract.inputs`; выход: `core.output` пишет в `modelOutputs`).

**Результат выполнения** (телеметрия для Debug UI): `nodeRuns` (статусы, входы/выходы, длительность, ошибки), `logs`, `outbox` (Telegram-отправки), `durationMs`, статус схемы.

Состояния:

```
IDLE → WAITING → RUNNING → SUCCESS | ERROR | STOPPED
```

**Telegram в runtime** — адаптер `runtime.telegram.send/sendPhoto`: сейчас — симуляция через outbox (сообщения видны в Debug-панели и демо-чате), в будущем — вызовы backend (см. [TELEGRAM.md](TELEGRAM.md)). Токен бота в frontend никогда не попадает.

## 6. Модели

Модель = контракт + внутренняя схема (canvas):

```
StoredModel = { id, name, version, contract: {inputs, outputs, error?}, canvas, updatedAt }
```

- Внешние порты модели формируются из контракта; внутри — обычная схема из обычных блоков.
- `core.input` («Вход модели») берёт значение по `config.portId` из `contract.inputs`.
- `core.output` («Выход модели») кладёт значение в `contract.outputs` по `config.portId`.
- **Модель внутри модели** — поддерживается: `executeModel` рекурсивен (лимиты runtime применяются ко всему дереву).
- Drill Down (открыть модель внутри редактора) — этап 2 ROADMAP (механизм выполнения уже есть).

Подробнее — [MODELS.md](MODELS.md).

## 7. Формат проекта и хранилище

`formatVersion: 1`, Zod-схема в `src/core/project/schema.ts` (единственный источник правды). Структура: canvas (узлы/соединения/viewport), models (контракты+схемы), variables, meta.

**ProjectStorage** — интерфейс: `list / get / save / remove`. Сейчас `LocalStorageAdapter` (ключ `nodezzle.project.<id>`). Автосохранение: debounce 900 мс после каждого изменения + синхронный flush на `beforeunload`/переходе.

Задел: API-адаптер (backend), история версий, команды/события — без изменения UI. Формат и миграции — [PROJECT_FORMAT.md](PROJECT_FORMAT.md).

## 8. Производительность (большой Canvas)

Уже заложенное:

- **виртуализация Canvas** — React Flow рендерит видимую область (pan/zoom без деградации);
- **лёгкие узлы** — кастомный узел рендерит только порты и статус (без тяжёлого дерева DOM);
- **минимизация обновлений** — Zustand с селекторами: узел перерисовывается только при изменении собственного статуса;
- **стабильные id** — соединения не зависят от порядков массивов;
- **бюджет выполнения** — runtime ограничен (500 шагов), UI не блокируется (a-синхронные блоки: Задержка).

План на большие проекты (этапы 2–5): пагинация/группировка слоёв, ленивая инициализация палитры, Web Worker для тяжёлого выполнения, оптимизация рендера рёбер (кэш отрисовки).

## 9. Безопасность

- Репозиторий публичный: **никогда без реальных секретов**. `.env.example` — только названия и фиктивные значения. `.env` в `.gitignore`.
- **Telegram Bot Token — только на backend** (в будущем). Frontend не хранит и не передаёт токен; runtime-адаптер в MVP — симуляция.
- Тип `secret` существует (маскируется в UI), но значения секретов в формат проекта в MVP не пишутся (секреты — через переменные окружения сервера).
- Zod-валидация при загрузке проектов: повреждённые/чужие данные не исполняются (runtime дополнительно проверяет существование блоков и соединения).
- XSS-защита: React экранирует вывод; пользовательский JSON в симуляторе парсится и показывается как данные (не HTML).

## 10. i18n

- Основой является **ru-RU**; остальные языки добавляются позже.
- `src/i18n/locales/ru.json` — все строки UI, категории, названия/описания блоков и портов, сообщения об ошибках.
- Технические идентификаторы (id блоков, портов, полей формата) — английские и **не переводятся**.
- Правила: любая новая пользовательская строка — новый ключ; новые блоки — свои `labelKey`/`descriptionKey`; новые ошибки — ключ `errors.*` (код ошибки = английский идентификатор, текст — русский).
