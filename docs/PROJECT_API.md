# Серверный API проектов — контракт ревизий (10B1, 0.5.47)

## Область действия

Это API черновика, не синхронизация Canvas и не история версий. Клиент
Dashboard 10A продолжает создавать/восстанавливать независимые копии.
Серверный режим редактора — следующий 10B2. Все запросы требуют действующую
HttpOnly-сессию и membership рабочего пространства. Чужой проект — 404,
без сессии — 401; знание project ID или revision не предоставляет доступ.

## Ответ с документом

`POST /api/projects`, `GET /api/projects/:id`, успешные `PUT` и `restore`:

```ts
{
  project: NodezzleProject; // прежний formatVersion: 1
  workspaceId: string;
  updatedAt: string;       // серверная ISO-дата, только для отображения
  revision: string;        // непрозрачный токен: 32 строчных hex-символа
}
```

Список `GET /api/workspaces/:id/projects` также включает revision в каждом
элементе. Ревизия — не число и не время. Её нельзя увеличивать/сортировать
или восстанавливать из meta.updatedAt; она не входит в документ схемы.
Для сохранения нужна ревизия **того документа, который был загружен и
редактировался**, а не более свежая метка, подставленная из списка.

## Условные изменения

| Запрос | JSON-тело | Успех |
|---|---|---|
| `POST /api/projects` | `{ workspaceId, document }` | 201, новый документ/ревизия; ID не должен существовать |
| `PUT /api/projects/:id` | `{ document, expectedRevision }` | 200, документ и новая ревизия |
| `POST /api/projects/:id/versions/:versionId/restore` | `{ expectedRevision }` | 200, восстановленный черновик и новая ревизия |
| `DELETE /api/projects/:id` | `{ expectedRevision }` | 200, `{ ok: true }` |

expectedRevision обязательна: отсутствие → **428 REVISION_REQUIRED**;
не строка нужного формата → **400 BAD_REQUEST**. Несовпадение с текущей
ревизией → **409 REVISION_CONFLICT**, без документа/свежей ревизии в ошибке.
Валидация тела, ID и доступа также может вернуть 400/401/404/413/415.
Невалидный запрос не меняет документ/дату/ревизию и не создаёт успешное
событие аудита. Аудит изменения добавляется только после успешного CAS.

Обновление — один SQL `UPDATE ... WHERE id = ? AND revision = ? RETURNING *`.
DELETE тоже условный. Даже запись того же документа и restore того же
снапшота выпускают новую случайную ревизию. Удаление/повторное создание
одного project ID не оживляет старую ревизию (защита от ABA). Два запроса
с общей базой не могут успешно перезаписать друг друга. Если проект успели
удалить, повторное обращение может получить 404 вместо конфликта.

Сессия и membership проверяются до и **после** await чтения тела PUT,
restore и DELETE. Нельзя начать медленный запрос, выйти из аккаунта и
потом дописать тело, сохранив доступ к изменению черновика.

## Снапшоты и LIVE

GET снапшота не выдаёт ревизию актуального черновика. Для restore нужна
ревизия черновика из GET проекта, не ID/дата версии. Restore не изменяет
сам снапшот или опубликованную LIVE-версию; запоздалое сохранение со старой
базой после restore получает конфликт. Создание снапшота и публикация не
редактируют документ черновика, поэтому не меняют его ревизию. Публикация
именно выбранной клиентом ревизии — отдельный будущий контракт, не функция
10B1. Нет автоматического merge или force-overwrite.

## Клиент и неопределённый исход

`src/lib/server-project-api.ts` — отдельный строгий клиент для будущего
редактора: load/save/restore/remove, проверка схемы, project ID и новой
ревизии ответа. Старый ответ без revision/workspaceId не считается готовым
к серверному редактированию. Same-origin cookies, ожидание до 15 секунд,
никаких автоматических GET → подстановка свежей ревизии → повтор PUT.

При timeout/обрыве/ошибке после записи сервер **мог сохранить** документ.
Нельзя считать это откатом. Повтор со старой ревизией безопасно откажет,
но клиенту ещё предстоит в 10B2 сохранить пользовательские правки,
перечитать сервер и предложить решение. CAS — не exactly-once и не гарантия
доставки. Локальные проекты/уроки не переводятся на HTTP-flush в unload.

## Совместимость и обновление

Серверная миграция `012_project_revisions.sql` заполняет ревизии старых
строк; JSON, ID, даты, версии и связи не меняются. Повторный запуск мигратора
не перевыпускает ревизии. Формат проекта остаётся v1; новый формат БД
не означает новый формат документа.

**Старые ручные PUT/restore/DELETE без expectedRevision теперь отклоняются.**
Нужно сначала получить редактируемый документ через GET, затем передать
его revision. Существующие GET/POST копий 10A совместимы без обновления
интерфейса. При будущем деплое обновлять все процессы backend согласованно,
не запускать старый сервер с безусловным SQL UPDATE над общей БД и не
откатывать бинарный код без совместимого плана. Сделать резервную копию БД.
VPS в этом подэтапе не изменялся.

## Проверка без риска для рабочего проекта

Использовать только отдельный тестовый проект и аккаунт:

1. Создать серверную копию; дважды прочитать её GET — как две вкладки.
2. Из первой отправить PUT с её revision. Должны вернуться 200 и новая метка.
3. Из второй отправить другой PUT со старой revision. Ожидается 409, а GET
   должен показывать первую правку, не вторую.
4. Так же проверить restore/DELETE: старая база не меняет свежий документ.

Это проверка API, не инструкция по уже существующим кнопкам Canvas.
Автоматически покрыто HTTP-тестами, двумя SQLite-подключениями и клиентскими
unit-тестами. Все 89 прежних браузерных сценариев прошли регрессию.
