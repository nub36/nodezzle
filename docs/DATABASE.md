# DATABASE — Хранилище данных и база данных

**Обновлено:** 2026-09-14 (Этап 5, подэтап 5.3). Статусы — по легенде [MASTER_SPEC.md](MASTER_SPEC.md) §1.

## 1. Текущее состояние: РЕАЛИЗОВАНО (браузерное хранилище)

### 1.1 Адаптер хранилища
Точка подмены — интерфейс `ProjectStorage` (`src/core/project/storage.ts`):
`list() / get(id) / save(project) / remove(id)`. Реализация —
`LocalStorageAdapter` (MVP, без сервера). Замена на серверный
`ApiStorageAdapter` не затрагивает ни ядро, ни UI (см. [PROJECT_FORMAT.md](PROJECT_FORMAT.md)).

### 1.2 Ключи LocalStorage (фактические)

| Ключ | Содержимое |
|---|---|
| `nodezzle.project.<id>` | Один проект целиком (формат `NodezzleProject`, JSON) |
| `nodezzle-ui-v1` | Состояние UI-стора (вкладка библиотеки, избранное, недавние и т. д., `zustand/persist`) |

### 1.3 Целостность и сохранение
- Чтение — только через `tryParseProject` (Zod): невалидные данные отклоняются,
  неизвестные `formatVersion` не принимаются (задел под миграции).
- Автосохранение: дебаунс 900 мс после изменения + синхронный сброс при
  закрытии вкладки (`beforeunload`).
- История правок холста (до 100 снапшотов `узлы/рёбра/группы`) живёт в памяти
  (undo/redo) и не сохраняется отдельно.

## 2. Целевая модель: ЧАСТИЧНО РЕАЛИЗОВАНО (серверная БД)

Серверная БД реализуется в Этапе 5: встроенный `node:sqlite` (файл БД,
путь задаётся `NODEZZLE_DB_PATH`); схема меняется только нумерованными
идемпотентными миграциями `server/migrations/*.sql` (учёт — таблица
`schema_migrations`). Применены миграции: `001_users` (аккаунты),
`002_sessions` (сессии), `003_workspaces` (пространства и участники),
`004_projects` (проекты: документ `NodezzleProject` целиком + индексы).
Остальные таблицы целевой схемы добавляются следующими подэтапами
([06-BACKEND-PRODUCT.md](agent-plan/06-BACKEND-PRODUCT.md)).
Форма хранения — реляционная БД; документ проекта остаётся тем же форматом
(документ в колонке + индексы для списков).

### 2.1 Сущности

| Таблица | Поля (эскиз) | Назначение |
|---|---|---|
| `users` | `id`, `email`, `password_hash`, `name`, `created_at` | Аккаунты (страница Авторизация) |
| `workspaces` | `id`, `owner_id`, `name` | Рабочие пространства |
| `workspace_members` | `workspace_id`, `user_id`, `role` | Доступы (ролевой доступ) |
| `projects` | `id`, `workspace_id`, `name`, `kind`, `document(jsonb)`, `format_version`, `updated_at` | Проекты (весь `NodezzleProject` документом) |
| `project_versions` | `id`, `project_id`, `snapshot(jsonb)`, `label`, `created_at` | История версий: снапшот, сравнение, откат |
| `executions` | `id`, `project_id`, `status`, `started_at`, `duration_ms`, `log(jsonb)` | История выполнений |
| `secrets` | `id`, `workspace_id`, `name`, `value_encrypted`, `created_at` | Секреты (шифруются; в схемах — только `secret_id`) |

Переменные проекта и модели хранятся **внутри документа проекта**
(поля `variables[]` и `models[]` формата) — отдельные таблицы под них не нужны,
пока не появится требование общего хранилища между проектами.

### 2.2 Миграции
- Схема формата (`formatVersion`) и схема БД мигрируются раздельно.
- Новые опциональные поля формата не требуют миграции (старые документы
  валидны); ломка/переименование полей — только новая версия + мигратор
  ([PROJECT_FORMAT.md](PROJECT_FORMAT.md), «Версии и миграции»).
- Миграции БД — нумерованные, идемпотентные, только вперёд.

### 2.3 Бэкапы и обслуживание
- Регулярные дампы БД; экспорт/импорт проекта пользователем — отдельная
  функция (экспорт/импорт JSON — в планах [ROADMAP.md](ROADMAP.md), этап 5).

## 3. Правила

1. Ядро читает/пишет проекты только через `ProjectStorage` — никаких прямых
   обращений к хранилищу из компонентов.
2. Секреты в таблицы проектов не попадают (см. [SECURITY.md](SECURITY.md)).
3. Документ проекта — единственный источник структуры; таблицы лишь индексируют
   его для списков и истории.
